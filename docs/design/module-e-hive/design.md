# Module E 虫巢系统（Hive）— 设计文档

> 创建时间：2026-03-21
> 状态：待顾问评审
> 设计来源：泰伦虫族社会结构 + OpenRoom 事件总线 + Cat Cafe 频道化 + 当皇上三省六部

## Step 1 — Vision（愿景对齐）

### 一句话定位

**灰风虫巢 = 一个具备神经进化能力的任务型多 Agent 系统，低阶 Agent 通过战功积累可晋升至高阶，形成自优化的社会分工。**

### 与中轴的关系

| 现有中轴 | 虫群架构如何融入 |
|---------|-----------------|
| **Persona 轴** | 主脑（Overmind）是灰风人格的终极载体，所有子节点继承其意志片段 |
| **Session 轴** | 虫巢基地（Hive Spire）= Session 的物理化，任务在基地内孵化执行 |
| **Context Runtime** | 虫巢意识网 —— 所有节点共享的上下文池，进化决策的数据来源 |

### 为什么不是静态分工

参考项目的局限：
- **OpenRoom**：双 Agent 是固定的，Browser Agent 和 Vibe Agent 各司其职，不会互相转化
- **Cat Cafe**：三猫分工是 meta-rules 预设的，不会根据实际表现调整
- **当皇上**：六部是封建等级，吏部永远是吏部，不会因为战功变成内阁

GreyWind 的差异点：
- **进化制**：刀虫可以通过战功积累晋升为宿主，甚至小主脑
- **战功驱动**：不是预先设定谁做什么，而是根据历史表现动态调度
- **负向学习**：失败也会写入基因，避免重复错误

## Step 2 — Architecture（架构卡位）

### 2.1 虫群社会等级（Tyranid Hierarchy）

```
┌─────────────────────────────────────────────────────────────────┐
│                        主脑（Overmind）                          │
│              系统唯一，灰风人格的完整载体                           │
│         职责：战略决策、进化方向、跨巢协调、最终仲裁                  │
│         状态：永不沉睡，全局感知                                    │
└───────────────────────────────┬─────────────────────────────────┘
                                ↓ 孵化/分裂
┌─────────────────────────────────────────────────────────────────┐
│                     小主脑（Synapse Nodes）                       │
│              每个 Thread 一个，战术指挥中枢                        │
│         职责：任务分解、子节点调度、战果评估、晋升推荐               │
│         进化：可从高战功宿主晋升                                   │
└───────────────────────────────┬─────────────────────────────────┘
                                ↓ 分泌/召唤
┌─────────────────────────────────────────────────────────────────┐
│                     虫巢基地（Hive Spires）                       │
│              每个 Session 一个，资源与执行环境                      │
│         职责：任务孵化、节点生命周期管理、局部记忆缓存               │
│         特性：Session 结束 = 基地休眠，数据归档至主脑               │
└───────────────────────────────┬─────────────────────────────────┘
                                ↓ 寄生/转化
┌─────────────────────────────────────────────────────────────────┐
│                      宿主（Hosts）                                │
│              任务执行容器，可被不同类型的虫群单位寄生                 │
│         职责：承接具体任务、维护局部状态、汇报战果                   │
│         类型：代码宿主、搜索宿主、文件宿主、操控宿主...              │
└───────────────────────────────┬─────────────────────────────────┘
                                ↓ 寄生
┌─────────────────────────────────────────────────────────────────┐
│                 战斗单位（Warriors / 虫群士兵）                    │
│    ┌─────────┬─────────┬─────────┬─────────┬─────────┐         │
│    │ 刀虫     │ 枪虫     │ 脑虫     │ 翼虫     │ 地虫     │         │
│    │(执行者) │(侦察者) │(分析者) │(通信者) │(潜伏者) │         │
│    └─────────┴─────────┴─────────┴─────────┴─────────┘         │
│         职责：原子任务执行                                        │
│         进化：战功积累 → 晋升更高阶模板                           │
└───────────────────────────────┬─────────────────────────────────┘
                                ↓ 孵化
┌─────────────────────────────────────────────────────────────────┐
│                      工蜂（Rippers）                              │
│              最小执行单元，无智能，纯本能反应                       │
│         职责：数据搬运、格式转换、简单计算                          │
│         特性：数量庞大，可聚合临时 swarm 处理并行任务               │
└─────────────────────────────────┘
```

### 2.2 战斗单位类型详解

| 单位 | 原型 | 职责 | 典型任务 |
|------|------|------|----------|
| **刀虫（Hormagaunt）** | 刀虫 | 执行者 | 写代码、改文件、执行命令 |
| **枪虫（Termagant）** | 枪虫 | 侦察者 | 搜索信息、抓取网页、验证数据 |
| **脑虫（Zoanthrope）** | 脑虫 | 分析者 | 代码审查、逻辑分析、方案评估 |
| **翼虫（Gargoyle）** | 石像鬼 | 通信者 | 跨节点协调、消息广播、状态同步 |
| **地虫（Ravener）** | 蛇虫 | 潜伏者 | 后台监控、定时任务、事件监听 |

### 2.3 进化机制（核心差异点）

```
战功记录（Kill-mark）
├─ 任务完成度（是否达成目标）
├─ 效率指标（耗时、token 消耗、步骤数）
├─ 用户满意度（显式反馈 + 隐式信号）
└─ 创新性（是否找到更优解）

晋升路径（Evolution Paths）
├─ 工蜂 → 刀虫：成功执行 100 次原子任务
├─ 刀虫 → 宿主：主导完成 10 个复杂任务
├─ 宿主 → 小主脑：连续 5 次任务评分 S 级
├─ 小主脑 → 主脑候选：处理跨巢危机
└─ 降级：连续失败 → 退化为低级模板 / 休眠

模板基因（Gene-seed）
├─ 每个等级有标准 prompt 模板
├─ 晋升时继承上级模板 + 个人战功优化
└─ 失败经验也写入基因（负向学习）
```

### 2.5 与现有模块的交互

| 现有模块 | 交互方式 |
|---------|----------|
| **Voice Pipeline** | 用户语音 → 主脑入口，虫群执行结果 → TTS 播报 |
| **Context Runtime** | 虫巢意识网复用 thread/session 机制，小主脑管理 thread 内任务链 |

| **Memory** | 战功记录写入 memory.json，基因库存储为独立 YAML |

## Step 6 — 风险与应对

| 风险 | 说明 | 应对 |
|------|------|------|
| 进化阈值调参困难 | 晋升条件太松导致等级膨胀，太紧导致进化停滞 | 提供配置化阈值 + 自适应调整算法 |
| 战功评估主观性 | 用户满意度难以量化 | 结合显式反馈（👍/👎）+ 隐式信号（是否中断、重试次数）|
| 基因库膨胀 | 长期运行后基因库过大 | 定期归档休眠基因、相似基因合并 |
| 虫巢意识网性能 | 全节点共享上下文可能导致广播风暴 | 分层缓存：小主脑本地缓存 + 主脑全局缓存 |
| 调试困难 | 分布式 Agent 决策难以追溯 | 全链路日志 + 虫巢可视化面板 |

### A.2 关键补充设计

**1. 五级等级制（L0-L4）**
- L0: Drone — 原子任务
- L1: Unit — 有界 SOP
- L2: Host Specialist — 管理 Host 工作区
- L3: Submind — 领域级工作流治理
- L4: Overmind — 全局真理和调度权威

**2. BroodTask 核心数据结构**
```python
@dataclass
class BroodTask:
    brood_id: str
    thread_id: str
    goal: str
    executor_level_required: Literal["L0", "L1", "L2", "L3", "L4"]
    domain: Literal["code", "research", "desktop", "memory", "review", "file", "general"]
    host_binding: Optional[str] = None
    depends_on: List[str] = field(default_factory=list)
    review_gate: Literal["none", "light", "strict"] = "none"
    state: Literal["queued", "ready", "running", "blocked", "review", "done", "failed", "aborted"] = "queued"
```

**3. Context Packet 统一接口**
- 强制所有虫群节点通过统一接口消费上下文
- 禁止直接访问原始内存存储
- 防止存储后端演进时的二次适配

**4. 进化层完整流程**
```
Intake -> Isolation -> Trial -> Selection -> Adoption or Extinction
```
- **GeneCandidate**: 外部/内部基因候选
- **TrialBrood**: A/B 测试对照组和实验组
- **SelectionReport**: 吞吐量/成本/失败率等多维度评估
- **GenomeRegistry**: 基因版本和生存分
- **ExtinctionLedger**: 淘汰记录审计

**5. Phase 计划（顾问建议）**
- **E0**: 接口锁定（ContextPacket, BroodTask, MemoryScope）
- **E1**: 最小记忆和虫群基础（Overmind + 1 Submind + 1 Host）
- **E2**: 多 Host 执行（更多 Host 类型、审查门、优先级调度）
- **E3**: 进化层（GeneCandidate、TrialBrood、晋升/降级）
- **E4**: 检索和长期记忆升级（向量检索、SQLite 持久化）

### C.1 四大新增机制（已修正）

**1. 多频道暴露模型（Multi-Channel Visibility）← 修正**

**交互模式**：
- 左侧点击频道 → 中间显示该频道的对话流
- 右侧可切换显示不同面板（Hive/Trial/Ledger/Host）
- 用户在中间可直接 @小主脑 @主脑 参与对话
- Trial Channel 中用户可看到赛马各分支实时进度，可手动终止某分支

**为什么修正**：
- 用户直接可见左侧任务列表、中间对话流、右侧面板的三层结构
- 中间对话流展示小主脑、主脑、Agent 间的协作过程（类似 Cat Cafe 频道内对话）
- 用户可参与 @mention，可看到赛马分支实时进度并手动干预
- 透明比较是赛马机制的核心价值

**2. 条件赛马机制（Conditional Trial Broods）**
- 不是所有任务都赛马，只有复杂任务触发
- 复杂度分级：简单(单路) / 中等(单路+局部验证) / 复杂(多路赛马)
- 赛马必须在隔离环境中进行（独立频道/独立Hive Base/独立Host）
- 赛马结束后主脑收敛并选择胜者（用户可在 Trial Channel 看到全过程）

**3. 主脑分身裁判（Vision Arbiter / Dreamer Shadow）**
- 不是第二主脑，而是监督视角
- 维护愿景边界和 done-when
- 作为赛马比较的一致判尺
- 发现需求缺口建议上抛

**4. 小主脑复用优先、受控孵化**
- 小主脑是可复用治理资产，不是一次性消耗品
- 三态：常驻(Resident) / 试验(Trial) / 休眠(Dormant)
- 新增小主脑触发条件：新领域/复杂赛马/过载/退化/新策略验证
- 转正需持续正向增益+可量化优势

### C.2 复杂度分级建议

| 级别 | 触发条件 | 执行策略 |
|------|----------|----------|
| 简单 | 明确目标、低风险、有成熟 SOP | 单小主脑单路执行 |
| 中等 | 一定不确定性、需要验证 | 单小主脑 + 局部双路验证 |
| 复杂 | 高价值、高不确定、多路径可能 | 多小主脑并行赛马 |
| 关键 | 核心任务、不可失败 | 多小主脑 + 愿景分身持续监督 |
